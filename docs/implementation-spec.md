# 有機化合物ビンゴ 実装仕様書

改訂日：2026-10-29。レビュー後の合意内容を反映した実装基準とする。

## 1. 目的

KoiChem の既存 `bingo_kun` をベースに、高校化学の有機化合物を扱うビンゴ用アプリを作成する。

既存ビンゴくんのメイン画面・ランダム表示・履歴・セット選択などの操作感はできるだけ維持し、教材データ部分を「化合物マスター＋ビンゴセット＋構造式SVG」に置き換える。

過剰実装を避けること。既存機能を流用できる場合は作り直さない。

---

# 2. 基本方針

## 2.1 データ構造

以下を明確に分離する。

1. **アプリ本体**
2. **マスターデータ**
3. **ビンゴセット**
4. **カテゴリー定義**
5. **構造式SVG**

最低限、以下のような構成にする。

```text
/
├─ index.html
├─ data/
│  ├─ compounds.json
│  ├─ bingo-sets.json
│  └─ categories.json
└─ structures/
   ├─ methanol.svg
   ├─ ethanol.svg
   ├─ acetone.svg
   └─ ...
```

既存 `bingo_kun` が単一HTML中心であることを理由に、アプリ全体を大規模リファクタリングしない。

必要ならJS/CSSを分離してよいが、今回の主目的ではない。

React等へのフレームワーク移行は禁止。

## 2.2 既存機能を流用する際の変更点

既存の操作感を維持しつつ、以下の従来仕様は引き継がない。

- 設定表の30行固定：行数は登録件数に合わせる。初期32種をすべて扱えること。
- 最低5件・推奨22〜24件の制限と確認ダイアログ：廃止する。空のセットを作成・保存でき、抽選開始は表示ONが1件以上なら可能とする。
- ランダムな比較関数によるソート：Fisher–Yates方式へ置き換える。
- 旧アプリの保存キーと自由入力カード形式：そのまま流用しない。旧形式のインポート・エクスポートUIやデータ移行は初期版の対象外とする。

## 2.3 状態の区別

以下の状態を区別する。

- **共有データ**：GitHubに反映済みの化合物マスター・ビンゴセット・カテゴリー定義。
- **作業中データ**：同じタブ内で編集・試用するマスターとセット。GitHubへ反映するまで共有データは変更しない。
- **端末設定**：セットごとのON/OFF。GitHub保存とは独立してlocalStorageへ即時保存する。
- **ラウンド状態**：開始時に確定するセット名、化合物データ、セット内No.、対象化合物、抽選順と、進行に伴って更新する現在位置・履歴。開始時に確定したデータはラウンド中に変更しない。

設定画面を閉じても作業中データは保持する。作業中データはトークンなしで編集・試用できるが、ページ再読み込み後の復元は初期版では保証しない。

# 3. 用語

## マスターデータ

正式名称は画面上で、

**マスターデータ**

とする。

全化合物の正式な共通データを保持する。

ビンゴセットはマスターデータをコピーせず、必ず化合物IDで参照する。

---

## ビンゴセット

授業等で使用する化合物の組み合わせ。

例：

- 酸素を含む脂肪族化合物
- アルコール
- カルボン酸・エステル
- 定期考査範囲

など。

1つの化合物を複数のビンゴセットから参照可能。

---

# 4. 化合物マスターのデータ形式

`data/compounds.json`

各化合物は最低限以下を持つ。

```json
{
  "id": "ethanol",
  "nameJa": "エタノール",
  "nameEn": "Ethanol",
  "formula": "C2H6O",
  "functionalGroups": ["アルコール"],
  "skeletonCategory": "脂肪族",
  "tags": ["1価アルコール", "第一級アルコール"],
  "structureSvg": "structures/ethanol.svg",
  "note": ""
}
```

## id

英語ベースの固定ID。

例：

```text
ethanol
acetone
acetic-acid
2-propanol
methyl-acetate
```

IDは化合物の主キーとして使用する。

### 重要

アプリ上からIDを変更してはいけない。

日本語名等を変更してもIDは維持する。

---

# 5. マスターデータで編集できるもの

## アプリから編集可能

- 日本語名
- 英語名
- 分子式
- 官能基・構造の分類
- 骨格分類
- タグ
- 備考

官能基・構造の分類は**複数選択可能**。

例：

乳酸

```text
官能基・構造の分類：
・アルコール
・カルボン酸

骨格分類：
・脂肪族

タグ：
・ヒドロキシ酸
```

---

## アプリから変更不可

以下はCodex経由のみ。

- 新しい化合物のマスター登録
- 化合物のマスター削除
- 英語IDの変更
- 構造式SVGの新規作成
- 構造式SVGの修正・差し替え
- 官能基・構造カテゴリーそのものの追加・削除・名称変更
- 骨格カテゴリーそのものの追加・削除・名称変更
- タグ候補そのものの追加・削除・名称変更

アプリにはこれらを変更するUIを作らない。

---

# 6. categories.json

分類語彙はCodexで管理する固定マスターとする。

例：

```json
{
  "functionalGroups": [
    "アルコール",
    "エーテル",
    "ケトン",
    "アルデヒド",
    "カルボン酸",
    "エステル",
    "酸無水物",
    "炭素間不飽和結合",
    "ハロゲン化合物"
  ],
  "skeletonCategories": [
    "脂肪族",
    "芳香族"
  ],
  "tags": [
    "1価アルコール",
    "2価アルコール",
    "3価アルコール",
    "第一級アルコール",
    "第二級アルコール",
    "第三級アルコール",
    "多価アルコール",
    "ヒドロキシ酸",
    "ジカルボン酸",
    "高級脂肪酸",
    "飽和脂肪酸",
    "cis",
    "trans",
    "ハロホルム"
  ]
}
```

ユーザーは既存候補を化合物へ付与・解除できる。

自由入力で新しいカテゴリー名を増やさない。

画面上の分類軸名は「官能基・構造の分類」とする。JSONのキー名は `functionalGroups` を維持する。

「炭素間不飽和結合」はC=CまたはC≡Cを表す。C=Oは含めない。初期32種ではフマル酸・マレイン酸・無水マレイン酸に付与し、これらを「アルケン」とは分類しない。

---

# 7. ビンゴセットのデータ形式

`data/bingo-sets.json`

例：

```json
[
  {
    "id": "oxygenated-aliphatic",
    "name": "酸素を含む脂肪族化合物",
    "compoundIds": [
      "methanol",
      "ethanol",
      "1-propanol",
      "2-propanol"
    ]
  }
]
```

ビンゴセットには化合物の名称や構造式をコピーしない。

`compoundIds` のみ保持する。

---

# 8. セット内No.

ビンゴセットの一覧左端に、

```text
No.
```

を表示する。

No.は**そのビンゴセットの登録順の番号で、削除時のみ再採番する**。

マスター共通番号ではない。

例：

```text
1  メタノール
2  エタノール
3  アセトン
4  酢酸
```

## ON/OFF時

No.は変えない。

例：

```text
1 ON
2 OFF
3 ON
4 ON
```

のまま。

---

## 検索・絞り込み・ソート時

No.は変えない。

検索結果が、

```text
3
8
12
```

となってもよい。

---

## セットへ化合物を追加

セット末尾へ追加。

現在の最大No.＋1になる。

---

## セットから化合物を削除

残った化合物を1から振り直す。

例：

```text
1
2
3
4
```

から2番を削除した場合、

```text
1
2
3
```

へ再採番する。

実装上は `compoundIds` の配列順＋1からNo.を導出すればよい。

No.自体をデータとして重複保存する必要はない。

---

# 9. ビンゴセット管理

アプリから以下を可能にする。

- 新規ビンゴセット作成
- ビンゴセット複製
- 名前変更
- 削除
- マスターから化合物を追加
- セットから化合物を削除

---

## 新規作成

空のセットを作成する。

空のまま保存してよい。抽選を開始できない理由はメイン画面で示す。

セットIDは内部的に一意で変更不能。

`crypto.randomUUID()` 等でよい。

---

## 複製

現在のセットの、

- 登録化合物
- 順序

をコピーする。

新しいセットIDを発行する。

ON/OFF状態はコピーせず、新規セットなので初期状態は全てON。

---

## セット順

セット内化合物の並び替えUIは不要。

固定順でよい。

## 削除・選択中セットの扱い

セット削除は確認してから作業中データへ適用する。最後の1セットも削除可能とする。

セットが0件の場合は「ビンゴセットがありません」と表示し、設定画面で新規作成できるようにする。抽選は開始しない。

設定画面で編集対象のセットを変えただけでは、メイン画面の選択セットを変更しない。

進行中のラウンドはスナップショットを使い続けるため、作業中データからセットや化合物を削除しても変更しない。次回開始時に選択セットが存在しなければ残った先頭セットを選択し、0件なら空の状態を表示する。

---

# 10. マスターからセットへの追加

「化合物を追加」ボタンを設ける。

押すとマスター一覧を表示する。

以下を使って検索・絞り込み可能にする。

- キーワード
- 英語ID
- 日本語名
- 英語名
- 官能基・構造の分類
- 骨格分類
- タグ

複数の化合物を選択し、

**このセットに追加**

できるようにする。

既にそのセットへ登録済みの化合物は重複追加不可。

複数選択した化合物は、検索結果の表示順やクリック順にかかわらず、マスターの元の配列順でセット末尾へ追加する。このセットとの組が新規の化合物は初期状態ONとする。

未反映の削除後に同じ化合物を同じセットへ再追加した場合、ON/OFFについては削除の取り消しとして、保持している既存状態を維持する。ユーザーがON/OFFを明示的に変更した場合はその最新値を使い、マスター・セット編集の破棄ではその変更を戻さない。

---


絞り込み中はさらに、

```text

```

を表示する。

例：

```text
登録 31種 ｜ 表示ON 24種 ｜ 絞り込み結果 8種
```


英語ID等を確認できるUIも用意してよい。

# 12. 化合物名の編集

ビンゴセット内から日本語名を修正できるようにしてよい。

ただしこれは**セット固有の別名ではない**。

編集すると化合物マスターの `nameJa` を変更する。

同じ化合物を利用している全ビンゴセットへ反映される。

UI上、

```text
マスター共通
```

等を表示し、セットだけの変更と誤解しないようにする。

セット固有の名称上書き機能は作らない。

---

# 13. ON/OFF

ON/OFFはビンゴセットごとに持つ。

ただしGitHubへは保存しない。

端末ローカルの `localStorage` に保存する。

キーは、

```text
OrgoBingo:v1:onOff
```

など、OrgoBingo専用の名前空間を付ける。その中で `setId` と `compoundId` の組をキーとして管理する。既存ビンゴくんや他のKoiChemアプリの保存領域を読み書きしない。

---

## 初回

そのセットへ登録されている化合物は全てON。

---

## GitHub側でセットが更新された場合

既存化合物：

```text
その端末のON/OFF状態を維持
```

新しく追加された化合物：

```text
ON
```

削除された化合物：

```text
localStorage上の情報も削除
```

削除されたセットについても、そのセットのON/OFF情報を削除する。

ただし、削除情報の整理はGitHubへの反映成功後、または正常に取得・検証できた共有データで削除を確認した時点で行う。未反映のセット・化合物削除や、データ取得失敗だけを理由にON/OFF情報を削除しない。

作業中の削除を破棄した場合、削除前のON/OFF状態を維持する。未反映の新規セットだけに属する情報は、その新規セットの作成を破棄したときに整理してよい。

---

# 14. 一括ON/OFF

ビンゴセット画面に、

```text
表示中をすべてON
表示中をすべてOFF
```

を設置する。

対象は**現在の検索・絞り込み結果だけ**。

「表示中」は画面のスクロール範囲ではなく、現在の条件に一致する全件を指す。対象件数が0件なら一括操作を無効にする。

「すべてON」「すべてOFF」という曖昧な表記は禁止。

例：

カルボン酸だけ8件に絞って、

```text
表示中をすべてOFF
```

を押した場合、その8件だけOFF。

他の化合物は変更しない。

---

# 15. 検索・絞り込み

マスターデータとビンゴセットの両方に実装する。

## キーワード検索対象

- 英語ID
- 日本語名
- 英語名
- 分子式
- タグ

---

## 官能基・構造

複数選択可。

同じ分類軸内ではOR。

例：

```text
アルコール
カルボン酸
```

を選択した場合、

```text
アルコール OR カルボン酸
```

---

## 異なる分類軸

AND。

例：

```text
官能基・構造：
アルコール OR カルボン酸

骨格：
脂肪族
```

なら、

```text
(アルコール OR カルボン酸)
AND
脂肪族
```

---

## キーワード

さらにAND。

前後の空白は除去し、英字の大文字・小文字は区別しない。初期版では入力全体を1つの部分一致条件として扱い、検索対象フィールドのいずれかに一致すればキーワード条件を満たす。複雑な検索構文は作らない。

## タグ・未選択・件数

タグも複数選択可能とし、同じタグ軸内はOR、他の分類軸・キーワードとはANDとする。

選択がない分類軸は絞り込み条件にしない。条件を解除すれば全件へ戻る。

登録数はセット全体、表示ON数はセット全体のON件数、絞り込み結果数はON/OFFにかかわらず検索条件に一致する件数とする。

---

# 16. ソート

少なくとも以下を用意する。

- 元の順序
- 英語ID
- 日本語名
- 英語名
- 官能基・構造の分類
- 骨格分類

ソートは表示だけ変更する。

マスター配列順やビンゴセットの `compoundIds` の順番を変更してはいけない。

官能基・構造の分類のように複数値がある場合は `categories.json` の候補順で比較し、同じ比較結果の行は元の順序を維持する。他のソートでも同順位は元の順序を維持する。

---

# 17. メイン画面

既存 `bingo_kun` の操作方法を基本的に維持する。

上部に、

```text
化合物名
構造式
```

の2つの表示モードボタンを置く。

---

## 開始

ビンゴセット内でONになっている化合物だけを対象にする。

ランダム順を最初に決定し、同一ラウンド内では重複表示しない。

対象化合物IDの配列をFisher–Yates方式でシャッフルする。`sort(() => Math.random() - 0.5)` は使用しない。各段階で残りの範囲から均等に位置を選び、並び順の偏りを避ける。処理量は件数に比例する。

開始時に、選択セット名、対象化合物のデータ、セット内No.、対象ID一覧を複製してラウンド用のスナップショットとする。作業中データの編集、ON/OFF変更、GitHub保存・再取得は進行中の抽選対象・名称・構造式・履歴を変更しない。

変更は次回開始時から適用する。設定画面を閉じただけではラウンドをリセットしない。未反映の編集内容も同じタブ内で次回の抽選に利用できる。

メイン画面で別セットへ切り替える場合は、進行中ならラウンドをリセットする旨を確認する。キャンセル時はセットも進行状態も変更しない。

抽選開始前に対象SVGを事前読み込みする。読み込みが完了するまでは連続開始を防ぎ、失敗時は対象化合物を示して開始を止め、再試行可能にする。読み込み失敗の化合物を黙って抽選対象から除外しない。

---

## メイン枠

メイン表示枠をタップすると次の化合物へ進む。

既存ビンゴくんと同じ操作感にする。

---

## 化合物名モード

大きく日本語名を表示。

---

## 構造式モード

対応するSVGを大きく表示。

プロジェクター表示を前提に最大限大きくする。

---

## モード切替

進行中でも切替可能。

例：

現在「エタノール」が表示されているとき、

```text
化合物名 → 構造式
```

へ変更しても、別の化合物へ進まずエタノールの構造式を表示する。

抽選アニメーション中も切替可能とする。抽選の確定対象IDは変更せず、アニメーション中の候補と確定表示を現在のモードで描画する。抽選開始時のモードに対応する文字列やSVGだけを保持して、確定時に古いモードへ戻してはいけない。

モード切替で抽選順・現在位置・履歴件数を変更しない。アニメーション中の連続タップ・Space・Enterでは次の抽選を重ねて開始しない。

リセット・セット切替でラウンドを終了した場合、旧アニメーションのコールバックが表示・現在位置・履歴を書き換えないようにする。

---

# 18. 履歴

現在までに表示された化合物を下部へ表示する。

確定済みの化合物だけを、最新が先頭になる順序で表示する。現在の確定済み化合物も含む。抽選アニメーションの候補は履歴へ追加しない。

## 化合物名モード

履歴も日本語名。

## 構造式モード

履歴も構造式SVGのサムネイル。

モード切替時は履歴全体も即座に切り替える。

---

## 履歴操作

履歴は完全に閲覧専用。

タップ・クリックしても何も起こらない。

過去の化合物をメインへ再表示する機能は作らない。

---

# 19. 表示対象0件

ONの化合物が0件の場合はスタートさせない。

例：

```text
表示ONの化合物がありません。
設定画面で1件以上ONにしてください。
```

と表示する。

---

# 20. 構造式SVG

構造式はPNGではなく**SVG**を使用する。

## 理由

教室のプロジェクターで拡大してもぼやけないようにするため。

---

## 作図ルール

- 白背景または透明背景
- 黒主体
- 高コントラスト
- 結合線は十分太い
- 細すぎる線は禁止
- 元素記号を十分大きくする
- 小さすぎる添字は禁止
- `viewBox` を必ず設定
- 外部フォントファイルに依存しない
- PC・タブレット・大型プロジェクターで拡大可能
- 不要な装飾は付けない
- 高校化学教科書の構造式に近い表現
- 骨格式だけではなく、CH3、CH2、OH等が高校生に読み取りやすい半構造式を基本とする
- `viewBox` は文字・結合線が欠けない範囲で不要な余白を抑える
- メイン表示と履歴サムネイルの両方で文字・添字・結合線が判読できるようにする
- SVG内に解答となる化合物名や日本語の説明ラベルを描き込まない

SVGは管理された `structures/` 内の画像として表示する。名称・備考などの入力文字列をHTMLとして解釈しない。分子式の添字も安全にDOMを組み立てて表示し、未加工の入力を `innerHTML` へ挿入しない。

## cis/trans

フマル酸とマレイン酸は特に注意。

### フマル酸

必ずtrans。

2つのカルボキシ基をC=Cの反対側へ配置。

### マレイン酸

必ずcis。

2つのカルボキシ基をC=Cの同じ側へ配置。

両者はcis/transという文字だけで区別せず、名称を隠した状態でもカルボキシ基の配置から判別できることを確認する。

## 基本

以下だけGitHubへ保存する。

```text
compounds.json
bingo-sets.json
```

必要な変更があるファイルだけ対象とする。

`categories.json` とSVGはアプリから変更しない。

# 22. GitHubトークン

IonicFormula等と同じ思想を使用する。

GitHubへ保存するときだけ入力を求める。

## 禁止

- HTMLへ埋め込む
- JavaScriptへハードコードする
- localStorageへ保存する
- sessionStorageへ保存する
- ログへ出力する

入力したトークンはメモリ上でのみ使用。

# 24. 1回の反映＝1コミット

`compounds.json` と `bingo-sets.json` の両方が変更されていても、

**GitHub上では1コミットにまとめること。**

2ファイルをContents APIで別々にPUTして2コミットにしない。

GitHub Git Database APIを使用して、

```text
編集基準のmain HEAD SHAを確認
↓
そのSHAのbase tree取得
↓
変更ファイルのblob作成
↓
1つのtree作成
↓
基準SHAだけを親にした1つのcommit作成
↓
main refをforce: falseで更新
```

という方式を使用する。

1ファイルだけ変更の場合も同じ保存ロジックを使用してよい。

変更がない場合はコミットを作成しない。保存中はマスター・セットの編集と保存の多重実行を防ぎ、反映対象が途中で変わらないようにする。

## 保存結果が不明な場合

ref更新へ渡した作成済みコミットSHAを保持する。応答が途切れた場合は、現在のmain HEADと必要に応じてその履歴を読み、当該コミットがmainに反映済みか確認する。反映済みなら保存成功として扱う。

未反映でmainが基準SHAのままなら、同じコミットのref更新を再試行できる。別更新が入っていれば競合として停止する。状態を確認できなければ「保存結果を確認できません」と表示し、編集内容と確認に必要なSHAをタブ内に保持する。結果が分かるまで新たな保存コミットを作り直さない。

保存成功後は、成功したコミットのSHAを新しい編集基準にし、そのコミットの内容を反映済みデータとする。公開ページや既定ブランチから古いJSONを読み直して、成功済みの内容を巻き戻さない。

# 25. GitHub競合

初回の編集開始時にmain HEAD SHAを確定し、基準SHAとして保持する。`compounds.json`、`bingo-sets.json`、`categories.json` は、すべてその同じSHAを明示して取得する。

設定画面を閉じて開き直すだけでは、基準SHAや作業中データを取り直さない。最新データの読み直しは明示操作とし、未反映の変更がある場合は破棄を確認する。

通常の閲覧・抽選には公開ページの同梱データを使用できるが、公開ページのJSONと別途取得した最新HEAD SHAを編集基準として組み合わせてはいけない。

基準データの取得・検証が完了してからマスター・セットの編集を開始する。取得できない場合はその旨を表示し、取得済みの閲覧・抽選・端末ON/OFF操作は利用可能とする。編集開始のための読み取りにトークンは要求しない。

GitHubへ保存する直前に現在のmain HEADを再取得する。

一致していなければ保存しない。

例：

```text
GitHub側のデータが更新されています。
最新データを読み直してから再度編集してください。
```

自動マージは禁止。

強制上書き禁止。

`force: true` によるref更新は禁止。

ref更新はfast-forwardのみ。

保存中に別更新が入ってref更新が失敗した場合も、競合として停止する。

新しいHEADへ自動的に付け替えて同じ編集内容を保存し直してはいけない。競合時も作業中データと差分を保持し、「読み直す」を自動実行しない。最新データを読み直して編集をやり直す際は、未反映の変更を破棄することを確認する。

認証失敗・権限不足・通信失敗・API利用制限は競合と区別し、原因に応じた案内を出す。

# 26. 未保存変更

マスターやビンゴセットの編集はGitHub保存まで「未保存」とする。

変更がある場合、

```text
未反映の変更があります
```

を表示する。

未保存状態で画面再読み込みや離脱を行う場合は警告する。

ON/OFFはこれとは別で、即座にlocalStorageへ保存する。

未反映の編集内容は同じタブ内で試用できる。設定画面を閉じる、GitHub反映をキャンセルする、保存に失敗する、といった操作では破棄しない。

「未反映の変更を破棄」を明示操作として用意し、確認後に反映済みデータへ戻す。破棄で端末の既存ON/OFF設定や進行中ラウンドをリセットしない。

再読み込み・離脱時の警告はブラウザの標準機能を使う。ブラウザによって警告されない離脱もあるため、自動復元を保証する案内はしない。永続的な下書き保存やバックアップ管理機能は初期版では追加しない。

# 27. マスター保護

アプリからGitHub保存する際、以下を検証する。

- 化合物IDの追加がない
- 化合物IDの削除がない
- 化合物IDの変更がない
- `structureSvg` が変更されていない
- categories.jsonの定義外カテゴリーがない
- categories.jsonの定義外タグがない

IDと `structureSvg` は同じ基準SHAから取得した元データと比較する。分類・タグの配列形式、骨格分類の単一値、定義内の値であることも検証する。日本語名は空白のみを不可とし、名称・分子式・備考の型を検証する。

これに反する場合は保存禁止。

マスターの登録・削除・構造式変更はCodexのみ。

### ON/OFF

- 初回全ON
- 既存状態維持
- 新規追加はON
- 削除項目はlocalStorageから削除
- 削除の整理は反映成功または正常に検証済みの共有データに基づき、未反映の削除・取得失敗では消さない
- 未反映の削除を破棄すると既存ON/OFFが維持される
- 既存OFF項目を未反映のまま削除・再追加してもOFFを維持する。明示的にONへ変えた後に編集を破棄した場合はONを維持する
- 一括操作はスクロール範囲ではなく絞り込み結果全件だけに適用される
- OrgoBingo専用の保存領域を使う

### No.

- ON/OFFで変化しない
- ソートで変化しない
- フィルターで変化しない
- 追加は末尾
- 削除後は再採番
- 複数選択での追加はマスターの元の順序

### 表示

- 化合物名→構造式切替で現在の化合物が変わらない
- 履歴も同時に切り替わる
- 履歴クリックは無効
- OFF項目は抽選されない
- 同一ラウンドで重複しない
- Fisher–Yatesの結果が元の対象の順列であり、0件・1件・複数件で欠落や重複がない
- ONが0件では開始不可、1件以上で開始可能。空セットの作成・保存は可能
- 最後のセットを削除してもエラーにならず、新規作成へ進める
- アニメーション中のモード切替でも確定対象IDと表示モードが一致する
- 連続タップ・キー入力で抽選が二重進行しない
- リセット・セット切替後に旧アニメーションが状態を更新しない
- 進行中に設定を編集しても現在のラウンドは変わらず、次回開始時に反映される
- 別セットへの切替確認をキャンセルすると進行状態も選択セットも維持される
- SVG事前読み込み失敗では開始を止め、黙って対象を除外しない
- メイン表示・履歴サムネイルの両方で添字・結合線・cis/transの配置を確認する
- ボタン間隔を狭い表示・折り返しでも維持する
- 入力文字列がHTMLとして実行されない

### GitHub

- トークンを保存しない
- HEADが変化していたら保存停止
- 2ファイル変更でも1コミット
- force pushしない
- 読み込みJSONと基準SHAが一致し、異なる版のファイルを混在させない
- コミットの親とbase treeが基準SHAに一致する
- mainが保存中に進んだ場合も既存更新を上書きしない
- 保存成功・失敗・キャンセル時にトークン入力欄と保持参照を破棄する
- 保存成功・応答喪失のケースで、作成済みコミットの反映状態を確認できる
- 結果不明のまま保存を重ねてコミットを作り直さない
- 保存失敗・競合・キャンセルでも作業中データを保持する
- 未反映データの試用、設定画面を閉じた後の保持、明示的な破棄が機能する
- 保存成功後は成功したコミットを基準にし、古い公開データで巻き戻さない
- GitHub保存成功をPages公開反映完了として表示しない

プロジェクターの実表示確認は、上記のブラウザ検証とは別に行う。乱数の公平性について不安定な統計テストを追加するのではなく、方式と対象範囲の選び方を確認する。

# 37. 実装時の優先順位

以下の順で進める。

1. 現行 `bingo_kun` の挙動を確認
2. compounds.json・categories.json作成とデータ検証
3. 現行メイン画面を壊さず化合物データへ置換し、件数制限を整理
4. 32個のSVG作成
5. bingo-sets.json作成
6. localStorage ON/OFF
7. ビンゴセット設定画面
8. マスターデータ画面
9. 検索・フィルター・ソート
10. GitHub編集・保存
11. 競合・通信失敗・保存結果不明時の処理
12. プロジェクター実表示確認
13. 完成条件の確認

各段階で対応するロジック・ブラウザの検証を行ってから次へ進む。テストを最終段階まで先送りしない。新たな変更・失敗・未解決の懸念がなければ、通過済みの検証を理由なく繰り返さない。

一度に全面改修しない。

# 38. 完成条件

以下を満たしたら初期版完成とする。

- 初期32化合物が登録されている
- 全32化合物に構造式SVGがある
- メインで化合物名／構造式を切替可能
- タップでランダム・重複なし表示
- 履歴も表示モードへ追従
- 履歴はクリック不可
- ビンゴセットをアプリで作成・複製・名称変更・削除できる
- マスターからセットへ化合物を追加・削除できる
- セットごとに登録順のNo.を表示し、削除時のみ再採番
- ON/OFFを端末ローカル保存
- 登録数／ON数／絞り込み結果数を表示
- 「表示中をすべてON/OFF」が機能する
- マスター・ビンゴセット双方で検索・抽出・ソート可能
- 化合物名・分類・タグ等をアプリから修正可能
- マスターの登録／削除／ID／SVGはアプリから変更不可
- GitHubトークンは保存されない
- マスター／ビンゴセット変更を1コミットでGitHubへ反映
- GitHub競合時は自動マージせず停止
- 進行中ラウンドを固定し、設定変更は次回開始時から適用
- 抽選アニメーション中のモード切替・連続操作・リセットが整合する
- 編集データと基準SHAが同じ版である
- 未反映の内容を同じタブ内で試用でき、保存失敗時も保持する
- 保存結果不明時に反映状態を確認し、確認前に保存を重ねない
- 空セット・セット0件・ONが1件の場合も仕様どおり扱える
- 未反映の削除では端末ON/OFFを失わない
- ボタン間隔と必要なアクセシビリティを確保
- プロジェクターで構造式が十分鮮明に読める
- 現行ビンゴくんの使い勝手を不必要に悪化させていない

## 2026-10-30 表示の追加確定事項

- シャッフル候補は通常表示の95%サイズ、黒を不透明度20%で白地に重ねた淡いグレー（#ccc相当）。確定後は黒・通常サイズに戻す。名称／構造式の両モードに適用し、履歴・設定・印刷には適用しない。
